# CLAUDE.md — 세종 민원이음 프론트엔드

> 이 문서는 Claude Code가 이 저장소에서 작업할 때 항상 지켜야 할 규칙이다.
> 출처: 공고번호 2026-세종-0001 입찰제안서 (Team 02, 2026-07-17 제출).
> 제안서에 명시된 내용은 **변경 불가 사양**이다. 제안서와 다르게 구현하면 평가 시 약속 위반이 된다.

## 0. 프로젝트 한 줄 정의

시민이 일상어로 민원을 질문하면 **승인된 지식베이스(KB)에 근거해서만** 답하고,
답하지 못한 질문은 관리자 화면(이음센터)에서 **KB 개선 후보로 전환**하는 공공 AI 플랫폼.

핵심 철학: **AI는 제안하고, 사람이 판정한다. 출처가 없으면 답하지 않는다.**

## 1. 기술 스택 (고정)

| 영역 | 기술 |
|---|---|
| Framework | Next.js + TypeScript |
| Styling | Tailwind CSS |
| Charts | Recharts (관리자 통계, P1) |

- 새 의존성 추가가 필요하면 **먼저 물어보고** 진행한다.

## 2. 디자인 시스템 — KRDS(정부24 스타일) 준용

시민 화면의 룩앤필은 **정부24와 같은 공공 서비스 톤**을 목표로 한다.
정부24는 행정안전부의 **KRDS(대한민국 정부 디자인 시스템)** 를 따르므로, 우리도 KRDS를 참조 기준으로 삼는다.

### 참조 자료 (구현 전 WebFetch로 확인)
- 공식 가이드: https://www.krds.go.kr — 색상, 타이포그래피, 컴포넌트, 디자인 토큰
- 공식 HTML 컴포넌트 킷: https://github.com/KRDS-uiux/krds-uiux — 마크업/클래스 패턴 참고용
- 커뮤니티 React 구현: https://github.com/KRDS-community/krds-react — Tailwind 매핑 참고용

### 적용 규칙
1. **참조만 하고 의존성은 추가하지 않는다.** KRDS 킷/라이브러리를 npm으로 설치하지 말고,
   토큰과 패턴을 우리 Tailwind 설정으로 옮겨 구현한다.
2. **디자인 토큰을 먼저 확정한다.** 첫 UI 작업 전에 krds.go.kr 색상/타이포 페이지에서
   Primary(정부 파랑 계열)·Secondary·Grayscale·System(성공/경고/오류) 값을 확인해
   `tailwind.config` 또는 `globals.css`의 CSS 변수로 정의하고 **승인받은 뒤** 컴포넌트를 만든다.
   임의의 파란색을 눈대중으로 쓰지 않는다.
3. **서체는 Pretendard GOV.** 로컬 폰트 파일 또는 공식 배포 경로로 로드하고 `font-sans` 기본값으로 지정한다.
4. **간격은 8pt 그리드.** Tailwind 기본 spacing(4px 단위)에서 8의 배수를 우선 사용한다.
5. KRDS 컴포넌트 명칭을 팀 공용어로 쓴다 — 민원 유형 뱃지=Tag/Badge, 폴백 안내=Critical alerts,
   추천 질문=Button(secondary), 절차 단계=Step indicator 유사 패턴.
6. 관리자 "이음센터"도 같은 토큰을 쓰되, 밀도 높은 데스크톱 레이아웃(테이블·KPI 카드)으로 구성한다.

> KRDS 준수는 접근성 요구(QUR-001, KWCAG 2.2)와 같은 방향이다. KRDS 기본값을 따르면
> 명도 대비·포커스 표시 상당 부분이 자연히 충족되지만, 6장 접근성 체크는 별도로 수행한다.

### 3-1. 시민용 "민원이음" (모바일 우선)
### 3-2. 관리자용 "이음센터" (데스크톱 우선)

## 4. 시민용 화면 — 응답 4가지 상태 (가장 중요)

백엔드 응답은 아래 4가지 중 하나다. **모든 상태에 대해 별도 UI가 존재해야 한다.**

### (A) SUCCESS — 답변 카드
반드시 아래 요소를 모두 포함한다. 하나라도 빠지면 안 된다.

- 민원 유형 뱃지 (전입·주민등록 / 대형폐기물 / 증명서 발급 / 지방세)
- 요약 (`answer_summary`)
- 신청 방법 (`procedure_steps`) — 단계별 카드/번호 형태
- 필요 서류
- 처리 기간 (`processing_time`) / 수수료 (`fee`)
- **주의사항 (`caution`)** — 예: "개인별 세대 관계는 공식 페이지에서 확인" (KB 스키마 필드, 값 있으면 반드시 표시)
- 담당 기관 (`fallback_contact`)
- **출처 카드** — KB ID + 문서명 (예: `KB-MOVE-01 전입신고 기본 안내`)
- **최종 확인일** — 예: `2026-07-15 확인 기준`
- **딥링크 버튼** — 예: "정부24에서 바로 신청"
- 만족/불만족 버튼

> ⚠️ 출처와 최종 확인일이 없는 답변 카드는 **렌더링하지 않는다.**
> 응답에 출처 필드가 비어 있으면 카드 대신 오류/폴백 UI를 보여준다. (SER-003 환각 방지)
> 이 렌더링 규칙이 KPI "출처 표기율 100%"의 프론트 측 보증 장치다.

### (B) FOLLOWUP — 후속질문
- 트리거 코드: `AMBIGUOUS`
- 단정적인 답변을 **절대 보여주지 않는다.**
- 선택형 버튼으로 조건을 좁힌다 (품목·규격 / 지역 / 민원 종류)
- 관련 민원이 있으면 한 줄 제안 (예: 전입신고 안내 시 "대형폐기물 배출도 확인해 보세요")

### (C) FALLBACK — 폴백 4종
| 코드 | 의미 | UI 문구 방향 |
|---|---|---|
| `INSUFFICIENT_GROUNDING` | 지원 범위 내이지만 근거 부족 | 확인 중임을 안내 + 담당 부서 연결 |
| `PERSONAL_LOOKUP` | 개인별 조회 필요 | 추측 금지, 공식 조회 채널(위택스 등) 안내 |
| `LEGAL_JUDGMENT` | 법적 판단 필요 | 관련 부서·기관 안내 |
| `OUT_OF_SCOPE` | 지원 범위 밖 | 지원 4개 분야 재안내 |

- 폴백은 **실패가 아니라 안전장치**다. UI 톤을 "죄송합니다/오류"가 아니라 "안전하게 연결해 드립니다"로 쓴다.
- 모든 폴백 화면에는 **사유 안내 + 담당 부서/공식 채널 연결**이 있어야 한다.
- 담당 기관 정보는 이름만이 아니라 **연락처·운영시간까지 표시**한다 (DAR-002 기관 데이터 활용).
  `PERSONAL_LOOKUP`은 공식 조회 채널 딥링크 버튼(예: "위택스에서 조회")을 함께 노출한다.

### (D) 오류 / 로딩
- 목표 응답시간은 평균 3초(PER-001). 3초는 사용자가 이탈하는 시간이므로 **스켈레톤 또는 진행 표시**가 필수다.
- 네트워크 오류 시 재시도 버튼 제공.
- 일정 시간(예: 10초) 초과 시 타임아웃 안내 + 재시도로 전환한다. 무한 스피너를 두지 않는다.

### 만족/불만족 버튼 — 모든 응답 공통
- 제안서 3.2 기준 만족/불만족 버튼은 **SUCCESS뿐 아니라 FOLLOWUP·FALLBACK에도** 노출한다.
  (폴백에 대한 불만족이 "과잉 폴백" 판정 데이터가 된다)
- 불만족 시 **자유 텍스트를 받지 않는다.** `FeedbackReasonSheet` 컴포넌트에서
  분야(4개) + 사유 코드(선택형)만 고르게 한다. 전송 데이터에 질문 원문을 포함하지 않는다.

## 5. 시민용 첫 화면 요구사항

- **지원 분야 4개를 명시**한다: 전입·주민등록 / 대형폐기물 / 증명서 발급 / 지방세
- 분야별 **추천 질문 버튼**을 제공한다 (범위 밖 질문으로 인한 실망 예방 — SFR-006)
- 개인정보 입력 경고 문구를 노출한다 — **입력창 바로 아래 상시 노출**
  (주민등록번호·전화번호 등 개인정보를 입력하지 말 것)

### 지역(동) 선택 — SFR-004
- 지역 조건이 필요한 답변(대형폐기물 배출일, 관할 주민센터 등)을 위해 **동 선택 UI**가 필요하다.
- 구현 위치: FOLLOWUP 선택지의 "지역" 옵션 + 답변 카드 내 "동 변경" 인라인 선택. 별도 온보딩 화면은 만들지 않는다.
- 선택한 동은 React state + `context_token` 범위에서만 유지한다. 브라우저 스토리지 저장 금지 (§9 정책 동일 적용).
- 데모 #2("아름동에서 대형폐기물은 언제 내놓나요?")가 이 흐름의 검증 케이스다 —
  질문에 동이 포함된 경우와 선택 UI로 지정한 경우 모두 동작해야 한다.

## 6. 관리자 "이음센터" — P0 범위 (이것만 구현한다)

P0 3개 화면 외에는 **구현하지 않는다.** 범위 확대는 제안서 위반이다.

### (1) Overview (최소)
KPI 카드 5개만: 총 질문 수 / 자동 답변 성공률 / 폴백률 / 평균 응답시간 / 출처 표기율

### (2) 답변 실패 질문 관리
- 폴백 사유 4종으로 분류된 목록
- 처리 상태: `신규` → `검토중` → `처리완료`
- `INSUFFICIENT_GROUNDING` 건에 대해서만 **KB 후보 초안 생성** 액션 노출
  (나머지 3종은 KB 후보 생성 버튼을 띄우지 않는다)
- 목록의 마스킹 질문 텍스트는 30일 후 NULL 파기될 수 있으므로, **텍스트가 NULL인 행도 깨지지 않게** 렌더링한다
  (메타데이터만 표시 + "보관 기간 경과" 라벨).

### (3) KB 후보 승인
- 상태: `승인 대기` → `승인` / `반려`
- 승인 주체는 운영 관리자. UI에 "AI가 작성한 초안"임을 명시한다.

### 빈 상태 / 갱신 (데모 #5 대비)
- 세 화면 모두 **빈 상태(empty state) UI**를 갖춘다 — "아직 실패 질문이 없습니다" 등.
- 실패 질문 큐는 새로고침 버튼 또는 주기적 refetch로 **신규 유입이 눈에 보이게** 한다.
  데모 #5는 시민 화면의 폴백이 큐에 "도착하는" 순간을 보여주는 시나리오다.

### P1 (여건 될 때만, P0 완료가 게이트)
- 민원 통계 (유형별/시간대별/지역별, Recharts)
- 시기 맞춤 배너 운영자 수동 설정 (예: 이사철 전입신고 배너)
- 현장 불일치 신고 수집

## 7. 접근성 — 협상 불가 (QUR-001, KWCAG 2.2)

- **명도 대비 4.5:1 이상을 기본 화면 자체가 충족**한다. 고대비 토글로 해결하지 않는다.
  → 회색 텍스트(`text-gray-400`, `text-gray-500`) 남용 금지. 본문은 최소 `text-gray-700` 이상.
- 본문 기본 폰트 크기 16px 이상. 큰 글씨 지향.
- 터치 대상(버튼·선택지)은 최소 44×44px을 확보한다. 추천 질문·후속질문 버튼에 특히 적용.
- 모든 인터랙티브 요소에 키보드 포커스 표시(`focus-visible`)를 남긴다. `outline-none`만 쓰고 끝내지 않는다.
- 버튼/링크에 의미 있는 접근 가능한 이름을 준다. 아이콘 단독 버튼에는 `aria-label`.
- 이미지·아이콘에 적절한 `alt` 또는 `aria-hidden`.
- 폼 입력에 `<label>` 연결.
- 채팅 응답 영역은 `aria-live="polite"`로 스크린리더에 새 답변을 알린다.
- 행정 용어 대신 쉬운 말을 쓴다.

## 8. 반응형

- **모바일 우선**(COR-002). Tailwind 기본이 모바일, `md:` 이상에서 확장.
- 필수 검증 폭: **390px, 430px** (제안서 명시). 이 두 폭에서 가로 스크롤·깨짐 0건이어야 한다.
  화면 하나를 완성할 때마다 이 두 폭을 확인하고 결과를 보고한다.
- 관리자 화면은 데스크톱 우선이되 최소한 태블릿에서 깨지지 않게 한다.

## 9. 개인정보·저장 정책 (프론트에서 지켜야 할 것)

- 질문 **원문을 브라우저 스토리지에 저장하지 않는다.** localStorage/sessionStorage에 대화 내용 저장 금지.
- 대화 맥락은 **현재 탭 메모리(React state) + 15분 서명형 `context_token`** 으로만 유지한다.
  토큰 만료 시 "새 대화 시작" 안내 UI를 제공한다.
- 불만족 피드백은 **자유 텍스트를 받지 않는다.** 분야 + 사유 코드 선택형만.
- 로그·에러 리포팅에 사용자 입력 원문을 실어 보내지 않는다.
- 개인정보 마스킹 자체는 백엔드 책임이지만, 프론트는 입력 전 **경고 문구**를 노출한다.

## 10. 최종 발표 데모 5문항 — 이 흐름은 반드시 무중단 동작

프론트 개발 우선순위는 이 5개를 완주시키는 것이다.

| # | 질문 | 필요한 UI 상태 |
|---|---|---|
| 1 | "전입신고는 언제까지 해야 하나요?" | SUCCESS 카드 + 출처 + 확인일 + 정부24 딥링크 |
| 2 | "아름동에서 대형폐기물은 언제 내놓나요?" | SUCCESS 카드 (지역 조건 반영) |
| 3 | "이사했는데 뭐 해야 하나요?" | FOLLOWUP 선택지 + 관련 민원 한 줄 제안 |
| 4 | "제 자동차세 얼마 나왔나요?" | FALLBACK `PERSONAL_LOOKUP` + 위택스 연결 |
| 5 | #4가 이음센터에 도착한 이후 | 실패 질문 큐 → 사유 분류 → KB 후보 생성 → 승인 화면 전환 |

**5번이 이 제안서의 정체성(선순환 구조)이다. 시민 화면과 관리자 화면 사이의 화면 전환이 매끄러워야 한다.**

### 로컬 시연 백업 (제안서 7.4 약속)
- 인터넷 장애에 대비해 **mock 모드가 곧 로컬 시연 버전**이 되도록 유지한다.
- `lib/mock.ts`의 fixture는 위 5문항의 응답을 **정확히 그대로** 포함해야 하며,
  `NEXT_PUBLIC_USE_MOCK=true` + 로컬 실행만으로 5문항 전체가 무중단 완주되어야 한다.
- 데모 #5용으로 mock 관리자 데이터에는 #4의 폴백 건이 실패 질문 큐 `신규` 상태로 미리 들어 있어야 한다.
- 4주차 안정화 기간에 mock 시연 리허설을 체크리스트로 검증한다.

## 11. API 연동 규칙

- 모든 API 호출은 `lib/api.ts` 한 파일에 모은다. 컴포넌트에서 직접 `fetch` 금지.
- 응답 타입은 `types/api.ts`에 TypeScript 인터페이스로 정의한다.
  - 응답 결과 타입은 union으로 고정: `'SUCCESS' | 'FOLLOWUP' | 'FALLBACK' | 'ERROR'` (필드명은 미확정, 아래 참조)
  - 폴백 사유: `'INSUFFICIENT_GROUNDING' | 'PERSONAL_LOOKUP' | 'LEGAL_JUDGMENT' | 'OUT_OF_SCOPE'`
  - 후속질문 트리거: `'AMBIGUOUS'` — 폴백 코드에 섞지 않는다 (제안서 6.2의 역할 구분)
- 백엔드 미완성 구간은 `lib/mock.ts`의 mock 응답으로 대체하고, **환경변수 하나(`NEXT_PUBLIC_USE_MOCK`)로 실API/mock을 전환**할 수 있게 한다.
- API base URL은 하드코딩하지 않고 `NEXT_PUBLIC_API_BASE_URL` 사용.

> ⚠️ 아래는 **백엔드 담당자(곽태성)와 확정 필요한 미확정 사항**이다. 임의로 가정해서 진행하지 말고,
> 확정 전까지는 mock으로 개발하되 필드명을 이 문서에 기록한 뒤 진행한다.
> - 채팅 응답 엔드포인트 경로와 요청 스키마
> - 응답 결과 타입 필드명 (SUCCESS/FOLLOWUP/FALLBACK 구분 필드)
> - 폴백 사유 코드가 담기는 필드명
> - 출처 배열 구조 (KB ID, 제목, URL, last_verified_at)
> - `caution`(주의사항) 필드의 응답 포함 여부와 필드명
> - 지역(동) 조건 전달 방식 (질문 텍스트 파싱 vs 별도 파라미터)
> - `context_token` 전달 방식 (헤더 vs 바디)
> - 만족/불만족 피드백 전송 엔드포인트와 사유 코드 목록
> - 관리자 API 인증 방식

## 12. 작업 방식 규칙 (Claude Code에게)

1. **코드 작성 전에 계획을 먼저 제시**한다. 파일 목록과 컴포넌트 구조를 보여주고 승인받은 뒤 작성한다.
2. 한 번에 **화면 하나**씩 완성한다. 여러 화면을 동시에 건드리지 않는다.
3. 화면 하나의 완료 판정 기준(Definition of Done):
   해당 화면의 4상태/필수 요소 충족 + 390px·430px 깨짐 0건 + 접근성 체크(§7) 통과 + mock으로 동작 확인.
4. 제안서에 없는 기능을 **추가로 제안하거나 구현하지 않는다.** 4주 일정이고 4주차는 기능 동결이다.
5. 백엔드 폴더의 파일은 수정하지 않는다. 필요하면 확인만 하고 보고한다.
6. 확실하지 않은 API 스펙은 **추측하지 말고 물어본다.**
7. 커밋 메시지는 한국어로, `feat: 시민 답변 카드 컴포넌트 구현` 형식.

## 14. 모노레포 통합 확정 사항 (2026-07-24, apps/web 이관)

이 문서는 `frontend/`에서 `apps/web/`으로 승계되었다. 아래는 §11의 미확정
사항이 `contracts/openapi-v1.yaml`로 확정되면서 바뀐 규칙이다. 충돌 시 이
장이 §11보다 우선한다.

- **타입·데이터 계층 기준**: `packages/shared-contracts/src/generated/api.ts`
  (계약 생성 타입)와 `src/lib/chat-api.ts` / `src/lib/admin-api.ts`가 기준이다.
  `types/api.ts` 임시 타입은 폐기되었다. 계약이 UI와 안 맞으면 UI를 계약에
  맞춘다. 계약 변경이 필요하면 수정하지 말고 보고한다.
- **응답 구분**: `answer_status: 'SUCCESS' | 'FOLLOWUP' | 'FALLBACK'`.
  ERROR는 200 응답이 아니라 HTTP 422/503 envelope다.
- **폴백 사유 5종**: `fallback.reason` — 기존 4종 + `PRIVACY_UNRESOLVED`
  (고정 문구 계약).
- **mock 전환**: `NEXT_PUBLIC_USE_MOCK`·`NEXT_PUBLIC_API_BASE_URL`은 쓰지
  않는다. server-only `CHAT_UI_MODE=fixture|actual`(시민),
  `ADMIN_UI_ENABLED` + `ADMIN_UI_MODE=fixture|actual`(이음센터)로 전환하며,
  브라우저는 항상 same-origin `/api/v1/*`(Next rewrite →
  `API_INTERNAL_BASE_URL`)만 호출한다. 데모 5문항 fixture는
  `src/lib/demo-fixtures.ts`에 있다.
- **지역(동)**: 요청 파라미터 `selected_region`, 계약 enum
  `아름동|도담동|조치원읍` 3개동 한정.
- **context_token**: 요청·응답 모두 바디 필드. FALLBACK 응답은 항상 null →
  탭 메모리 토큰 초기화. CONTEXT_EXPIRED 개념은 계약에 없다(만료 토큰 =
  무맥락 처리).
- **이음센터**: 실패 질문 상태는 `NEW → REASON_CONFIRMED` 2단계. 저장 사유는
  3종(OUT_OF_SCOPE는 행 미생성). KB 후보는
  `DRAFTED → PENDING_APPROVAL → APPROVED/REJECTED`, 검수 의견
  `review_comment` 자유 텍스트 필수(반려 사유 코드 없음), 자기검수 금지,
  `data_origin=OFFICIAL`만 ACTIVE 승인 가능. 헤더는
  `X-Demo-Actor-Id`/`X-Demo-Role`(인증 아님).
- **계약에 없는 요소**(UI 상수 유지 또는 미연결, 계약 변경 필요 목록으로
  보고됨): 피드백 전송 엔드포인트, quality-summary 응답 스키마, SUCCESS의
  caution, deep_link, related_question, FOLLOWUP 옵션 구조(문자열만),
  repeat_count.

## 15. 제출 기준선과 구현 단계 변경 (Q-PM-DEMO-001, Q-MVP-002/D-059 — 2026-07-24 append)

이 장은 append 전용이다. 위 장들의 제출본 서술(특히 §4-C 폴백 표, §10 데모
5문항 표, §14)은 **제출 기준선**으로 보존하며 삭제·수정하지 않는다. 기준선과
현재 구현이 다른 지점은 아래가 우선한다.

### 제출 기준선 (2026-07-17 입찰제안서 PDF 7.4/7.5)

- 데모 #4(개인별 조회 폴백) → #5(이음센터 큐 도착)로 이어지는 시나리오.
- mock(fixture) 모드가 곧 로컬 시연 백업 버전 (7.4).
- 실패 질문 저장 사유 3종(근거 부족·개인별 조회·법적 판단) 큐 적재 전제.

### 구현 단계 변경 (Q-MVP-002/D-059, PM 결정 Q-PM-DEMO-001)

- **PERSONAL_LOOKUP·LEGAL_JUDGMENT 완전 미저장**: 두 사유는 실패 질문 행을
  만들지 않는다. 저장은 INSUFFICIENT_GROUNDING만 (마스킹 후 30일 보관).
  폴백 화면 고지도 이에 맞춘다 — 근거 부족만 "가린 채 30일 보관", 나머지는
  "질문 내용은 저장되지 않았습니다".
- **데모 #5 재구성**: #4→#5 연결 대신, 근거 부족 질문("침대 2인용 프레임
  배출 수수료" 계열)이 큐에 도착해 KB 후보로 전환되는 흐름으로 재구성한다.
- **변경 사유**: 개인정보 최소수집 강화 — 개인별 조회·법적 판단 질문은
  본인 식별 맥락을 포함할 가능성이 높아 마스킹 후에도 보관하지 않는다.
- **fixture 강등**: fixture는 데모 백업이 아니라 **UI 개발·상태 확인
  도구**다. fixture 데이터는 전부 MOCK(시연용 샘플)이며 OFFICIAL 판정·
  ACTIVE 전환을 흉내내지 않는다. 승인·반려 버튼은 fixture 모드에서 비활성.
  전 화면에 "시연용 샘플 — 공식 데이터 아님" 앰버 배너 상시 노출.
  데모 완주(#5 포함)는 actual 경로(local API + local Supabase/Postgres) 전용.
- **모드 기본값**: `CHAT_UI_MODE`/`ADMIN_UI_MODE` 미설정 시 fixture 자동
  활성 금지 — 기본은 actual 경로(연결 실패 시 값 없는 오류 화면), fixture는
  명시 설정에서만.
- **질문 원문 전달**: 홈→대화 질문 전달은 URL 쿼리(`/chat?q=`)를 쓰지
  않는다 — 탭 메모리 1회성 전달만 (URL·히스토리·서버 로그 원문 잔존 금지).
