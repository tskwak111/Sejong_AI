# 1. 사업 이해

## 1.1 RFP의 핵심 문제

RFP는 단순·반복 문의가 전화와 방문에 집중되고, 야간·주말에는 즉시 안내받기 어려우며, 부서별 안내 기준이 달라 시민이 서로 다른 답을 들을 수 있다는 문제를 제시한다. 발주처가 원하는 것은 범용 챗봇이 아니라 다음 책임을 갖는 공공 민원 안내 체계다.

- 시민의 일상어 질문을 이해한다.
- FAQ·조례·고시·업무 매뉴얼 등 공식 근거를 검색한다.
- 절차·서류·처리 기간·수수료를 구조화한다.
- 답변마다 출처를 표시한다.
- 정보가 부족하거나 개인별 조회가 필요한 질문은 담당 기관으로 연결한다.
- 질의·응답 결과를 비식별 형태로 관리해 품질을 개선한다.
- 모바일 우선·개인정보 최소수집·접근성을 준수한다.

## 1.2 발주처가 실제로 구매하는 가치

| 요구 | 구매 가치 | 본 제안의 대응 |
| --- | --- | --- |
| 24시간 안내 | 근무시간 외 기본 민원 접근성 | 모바일 /chat과 구조화 답변 |
| 정보 정확성 | 안내 기준 통일과 행정 신뢰 | 공식 ACTIVE KB와 서버 결합 출처 |
| 민원 완료 지원 | 재검색·재문의 감소 | 절차·서류·수수료·기관 카드 |
| 안전한 한계 | 잘못된 답변의 행정 위험 감소 | 4개 폴백과 사람 승인 |
| 운영 개선 | 부족한 FAQ를 발견·보완 | 실패 질문→KB 후보→승인 |
| 설명 가능한 품질 | AI 도입 성과·한계 보고 | 표본 테스트·이벤트 KPI·감사 이력 |

## 1.3 성공의 정의

본 사업은 AI가 많은 질문에 답하면 성공한 것이 아니다. 다음이 모두 작동해야 한다.

1. 답변 가능한 질문은 공식 출처와 함께 구조화해 안내한다.
2. 모호한 질문은 추측하지 않고 후속질문을 한다.
3. 개인 조회·법적 판단·지원 범위 밖 질문을 구분한다.
4. 사용자 원문을 애플리케이션 DB에 저장하지 않는다.
5. 근거 부족 질문만 KB 후보로 작성한다.
6. 작성자와 승인자를 분리한다.
7. 승인된 ACTIVE KB만 시민 답변에 사용한다.
8. 승인 전에는 폴백되던 질문이 승인 후 출처 기반 답변으로 바뀐다.

# 2. 문제와 대표 사용자

## 2.1 대표 사용자

### 김지민(가명), 33세, 아름동으로 이사한 직장인

| 항목 | 내용 |
| --- | --- |
| 생활 상황 | 최근 세종시 아름동으로 이사한 맞벌이 직장인 |
| 이용 시간 | 평일 21시 이후, 주민센터·콜센터 운영 종료 후 |
| 디지털 역량 | 모바일 서비스에는 익숙하지만 행정 용어와 담당 부서를 모름 |
| 주요 과업 | 전입신고, 등본 발급, 이사 폐기물 처리, 공식 담당 기관 확인 |
| 현재 행동 | 포털 검색→여러 페이지 비교→다음 날 전화·방문 |
| 핵심 불편 | 공식성·최신성·개인 적용 여부를 판단하기 어려움 |
| 기대 결과 | 지금 해야 할 일, 준비물, 근거, 담당 기관을 한 번에 확인 |

## 2.2 가장 중요한 문제 상황

> “이사했는데 전입신고부터 무엇을 해야 할지 모르겠다. 검색 결과는 많지만 어느 정보가 공식이고 최신인지 판단하기 어렵고, 침대를 버리는 수수료와 가까운 주민센터도 함께 알고 싶다. 지금은 전화할 수도 없다.”

문제는 정보가 없다는 데 있지 않다. 정보가 여러 문서와 사이트에 흩어져 있고, 시민이 자신의 상황에 필요한 공식 정보만 골라 다음 행동으로 연결하기 어렵다는 데 있다.

## 2.3 문제 정의

> **근무시간 외에 민원 정보를 확인하려는 시민은 분산된 행정 정보에서 자신의 상황에 맞는 공식 절차와 담당 기관을 빠르게 찾기 어렵고, 담당자는 같은 단순 문의를 반복해서 처리한다. 따라서 시민의 일상어를 공식 행정 지식과 연결하고, 불확실한 질문은 안전하게 사람과 공식 채널로 전환하며, 실패 질문은 검수 가능한 지식 개선으로 이어지는 운영형 민원 AI가 필요하다.**

# 4. 대표 사용자 흐름

![대표 사용자·관리자 개선 흐름](assets/representative_flow.png)

## 4.1 정상 답변

사용자가 `이사했는데 전입신고 어떻게 해요?`라고 입력하면 백엔드는 개인정보를 먼저 마스킹하고, 질문을 전입·주민등록으로 분류하며, 승인된 공식 KB를 검색한다. 시민에게는 다음을 카드로 제공한다.

- 민원 유형
- 핵심 요약
- 신청 방법
- 필요 서류
- 처리 기간
- 수수료
- 담당 기관
- 공식 출처명·링크·확인일

## 4.2 모호한 질문

`신고하고 싶어요`처럼 정보가 부족한 질문에는 다음 선택지를 제공한다.

1. 전입·주민등록
2. 등본·초본 등 증명서
3. 대형폐기물
4. 지방세
5. 그 밖의 민원

모호한 질문은 시스템 실패가 아니므로 실패 질문 목록에 저장하지 않는다.

대화 화면은 현재 탭 메모리에서만 이어지며, 후속질문에는 질문·답변·개인정보를 포함하지 않는 15분 서명형 client-carried context token을 사용한다. 서버 세션이나 raw transcript를 저장하지 않고 새로고침 시 문맥을 초기화한다.

## 4.3 안전 폴백

| 코드 | 사유 | KB 후보 | 시민에게 제공할 다음 행동 |
| --- | --- | --- | --- |
| INSUFFICIENT_GROUNDING | 지원 범위 안이지만 승인 근거 부족 | 가능 | 공식 확인 경로·담당 기관 |
| PERSONAL_LOOKUP | 본인 인증·개인 행정정보 필요 | 불가 | 위택스·정부24·담당 부서 |
| LEGAL_JUDGMENT | 법적·자격·행정 처분의 판단 필요 | 불가 | 일반 정보와 전문 담당자 |
| OUT_OF_SCOPE | 현재 4개 지원 분야 밖 | 불가 | 지원 범위와 관련 공식 기관 |

## 4.4 개선 전후 데모

질문: `침대 2인용 프레임 수수료가 얼마예요?`

- 공식 수수료 정보는 존재하지만 초기 ACTIVE KB에는 등록하지 않는다.
- 승인 전에는 `현재 승인된 지식베이스에 세부 근거가 등록되어 있지 않다`고 폴백한다.
- 운영자가 세종시설관리공단 공식 페이지를 확인해 후보를 작성한다.
- 작성자와 다른 승인자가 2인용 침대 프레임 10,000원과 출처를 검수한다.
- 승인 후 동일 질문은 10,000원과 출처 카드를 반환한다.

# 5. 해결 방안 상세

## 5.1 시민용 민원 AI 플랫폼

### 자연어 질문·의도 분류

- 4개 지원 분야와 범위 밖을 분류한다.
- 모호성은 별도 상태 FOLLOWUP으로 반환한다.
- 분류 결과는 구조화 JSON으로 반환한다.

### 공식 KB 기반 구조화 답변

```json
{
  "intent": "MOVE_IN_REPORT",
  "answer_status": "SUCCESS",
  "summary": "...",
  "procedure_steps": ["..."],
  "required_documents": ["..."],
  "processing_time": "...",
  "fee": "...",
  "department": "...",
  "source_ids": ["KB-MOVE-01"]
}
```

출처명·URL·확인일은 LLM이 생성하지 않는다. 서버가 `source_ids`에 대응하는 KB 메타데이터를 응답에 직접 결합한다.

### 지역 선택·기관 안내

MVP는 GPS를 사용하지 않는다. 시민이 아름동·도담동·조치원읍을 직접 선택하고, 시스템이 지역과 민원 유형을 조합해 공식 기관을 안내한다.

```text
selected_region + intent → official office record
```

SFR-004는 **대체·부분 구현(P0)**으로 표시한다. GPS·실제 거리 정렬은 P2다.

### 접근성 P1

- 핵심 용어 사전 기반 쉬운 말 전환
- 주요 본문 16px→20px, 카드 제목 20px→24px
- 일반 본문과 배경 대비 4.5:1 이상
- 상태를 색상만으로 표현하지 않음
- 키보드 포커스와 모달 포커스 복귀

## 5.2 관리자용 AI 민원 운영센터

실제 페이지는 `/admin` 하나이며 다음 탭과 모달로 구성한다.

### 역할 분리

## 7.3 검색 전략

KB가 20건이므로 복잡한 벡터 검색만으로 판단하지 않는다.

1. 지원 분야 메타데이터 필터
2. 키워드·동의어 검색
3. 임베딩 유사도 보조
4. 최소 근거 기준과 필수 필드 확인
5. 기준 미달 시 폴백

## 7.4 LLM 공급자

공급자는 Upstage direct API exact `solar-pro3`다. 합성 평가를 먼저 수행했고 strict schema
27/30으로 FAIL했다. 이후 local/private 입찰 시연 MVP에서는 supported intent·안전한 마스킹·
ACTIVE/OFFICIAL 검색·근거 gate를 모두 통과한 시민 요청만 8초·1 attempt·concurrency 1·
process cap 30으로 호출하도록 별도 승인했다. `LLMProvider` 인터페이스를 유지하고, 모델은
summary와 server-issued fact ID만 제안한다. strict schema·ID·fact 검증에 실패하면 결과 전체를
버리고 서버가 공식 KB template와 source를 결합한다. public/remote/실제 기관 운영은 별도 승인
전까지 disabled/template 경로만 사용한다.

# 8. 개인정보·보안·접근성

## 8.1 외부 LLM 호출 전 마스킹

```text
local/private 지원 범위 시민 입력
→ 백엔드 PII 탐지·마스킹
→ deterministic policy·ACTIVE/OFFICIAL·grounding gate
→ 마스킹 질문, 최소 KB와 server-issued fact ID만 Upstage 전달
→ 서버 strict 검증·공식 fact/source 결합 또는 전체 template fallback
→ 원문 DB 미저장
```

FOLLOWUP·privacy unresolved·근거 부족·개인조회·법적판단·지원 범위 밖 요청은 provider call
0이다. public/remote/실제 기관 운영 요청도 별도 개인정보·보안·비용·배포 승인 전까지
Upstage 또는 다른 외부 LLM에 전달하지 않고 ACTIVE KB 기반 template 경로만 사용한다.

## 8.2 로그 분리

### 모든 요청

질문 문장 없이 intent, 상태, 사유, source_count, response_time_ms, 선택 지역 등 이벤트 메타데이터만 저장한다.

### 실패 질문

지원 범위 내 개선 검토 질문에만 masked_question을 추가한다. OUT_OF_SCOPE는 텍스트나 failed_questions 행을 저장하지 않는다. 마스킹 실패 질문은 생성 후 30일이 지나면 행을 삭제하지 않고 masked_question만 NULL로 파기하며 파기 시각을 기록한다. 비텍스트 메타데이터와 KB 후보 연결은 유지한다. 30일은 MVP 내부 운영 기준이다.

## 8.3 감사 로그

상태·행위·대상 ID·변경 필드명만 저장하고 질문·답변 전체 스냅샷을 저장하지 않는다.

## 8.4 보안 테스트

- PII 포함 질문의 DB·서버로그 원문 0건
- 외부 LLM 테스트 더블 payload의 마스킹 확인
- 정책/근거 gate 밖 자유 입력의 Upstage adapter 도달 0건
- DRAFT/PENDING KB 검색 노출 0건
- 작성자 본인 승인 거부
- KB 후보 개인정보 입력 시 저장 차단

# 16. 결론

세종 민원이음의 목표는 답변 수를 최대화하는 것이 아니다. 공식 근거가 있으면 출처와 함께 끝까지 안내하고, 근거가 없거나 개인별·전문적 판단이 필요한 질문은 명확한 사유와 다음 행동을 제공한다.

동시에 실패 질문을 오류로 버리지 않는다. 지원 범위 안의 근거 부족 질문만 개인정보를 제거해 운영자가 검토하고, 공식 출처 기반 후보로 작성하며, 다른 승인자가 검수한 정보만 시민 답변에 반영한다.

> **시민에게는 신뢰할 수 있는 안내를, 담당자에게는 통제 가능한 개선 도구를 제공한다.**
