## 5. 설계 결정과 대안

### 증거

- working source `8e02950`의 system prompt는 `JSON 객체`를 명시했고 provider 20/20 usage,
  corrective 60/60 PASS였다.
- current Hybrid RAG system prompt는 catalog 압축 과정에서 그 문장을 제거했다.
- current actual provider 9개 message를 값 없이 검사한 결과 explicit `json` instruction은 0/9다.
- adapter는 계속 `response_format={"type":"json_object"}`를 보낸다.
- OpenAI-compatible JSON object mode의 primary API reference도 message가 JSON 출력을
  지시해야 한다고 설명한다. Upstage의 exact 4xx body를 보관하지 않았으므로 이는 강한
  inference이지 actual 확정은 아니다.

### 1순위 가설

catalog 크기나 계정 상태보다, `json_object`와 명시적 JSON instruction의 불일치가 request
validation 4xx를 만든다.

### 제외한 대안

- key 재발급·결제: console evidence와 맞지 않아 먼저 하지 않는다.
- timeout 확대: HTTP response 9/9라 원인과 맞지 않는다.
- token cap 확대: provider 2xx 후 usage reject가 아니라 pre-generation 4xx라 우선순위가 낮다.
- 여러 payload 변경 동시 적용: 원인을 분리할 수 없어 금지한다.
