## 5. 설계 결정과 대안

### 선택

1. PII 마스킹·policy gate와 고신뢰 결정론 경로를 먼저 유지한다.
2. 필요한 경우에만 Upstage가 서버가 제공한 ACTIVE/OFFICIAL catalog에서 topic을 제안한다.
3. 서버가 intent·topic·현재 ACTIVE/OFFICIAL projection·source를 재검증한다.
4. 기존 approved facts를 먼저 사용하고 topic descriptor·synthetic UAT/negative fixture만
   별도 versioned artifact로 추가한다.
5. 새 factual detail은 새 official-data/PM 승인 cycle 전까지 근거 부족으로 닫는다.

### 이유

분류 recall을 개선하는 모델 판단과 시민에게 제시하는 행정 사실의 권위를 분리하면,
자연어 표현은 넓게 받으면서 답변·출처는 승인 KB 밖으로 나가지 않는다.

### 고려했지만 선택하지 않은 대안

- vector DB/embedding: 20 topic MVP에는 비용·의존성·운영 복잡도가 과하다.
- 모델 일반지식 보충: 공식 KB 근거 원칙을 위반한다.
- immutable `.2`에 alias 직접 추가: 데이터 계보와 PM 승인 증거를 훼손한다.
- 냉장고·재산세 detail KB 선행: retrieval 결함을 남긴 채 일정과 검수만 늘린다.

## 9. 보안·개인정보·접근성·성능 영향

- Privacy: 외부 분류 입력은 마스킹 완료 질문과 closed catalog뿐이며 원문 저장 변화 0.
- Security: topic 제안은 권위가 아니며 server가 ACTIVE/OFFICIAL membership을 재검증한다.
- Accessibility: 제품 UI 변경 없음.
- Performance/cost: provider call 0. 목표 catalog는 최대 20 topic으로 bounded된다.

## 10. 데이터와 출처 영향

- 공식 데이터: immutable `.2` read-only; local 20th mutation 0.
- mock/AI 생성: factual data 0. 향후 UAT는 synthetic/non-official 표기를 강제한다.
- schema/lineage: 기존 DATA-SEED-002 계보 유지.
- verified date: 기존 record의 값을 변경하지 않는다.

## 11. 인간이 반드시 알아야 하거나 승인할 내용
