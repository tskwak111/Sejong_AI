## 5. 설계 결정과 대안

### 선택

- 모델은 bounded summary와 server-issued procedure/document/time/fee/department ID만 제안한다.
- 서버가 ID를 승인 KB의 공식 text로 materialize하고 source/office/policy를 결합한다.
- timeout, provider 오류, schema, unknown ID, 누락·중복 또는 fact drift가 하나라도 있으면 AI
  일부를 사용하지 않고 답변 전체를 deterministic template로 대체한다.
- SUCCESS 작성 방식은 `answer_mode=GENERATED|TEMPLATE`로 공개하고 접근 가능한 텍스트 배지를
  제공한다.

### 이유

AI가 질문에 맞는 문장을 만들 수 있게 하면서 행정 fact와 출처는 서버 권위로 고정할 수 있다.
LLM-002의 27/30 schema 결과도 시민 기능 실패가 아니라 template 전환으로 흡수한다.

### 고려했지만 선택하지 않은 대안

- AI 없이 template만 유지: 가장 안전하지만 사용자가 원하는 local 시연의 맞춤 표현을 제공하지 못함.
- summary-only: 더 작은 위험 표면이나 사용자의 후속 Q-LLM-012=B가 대체함.
- fact/source 자유 생성: 환각과 공식 출처 위조 위험으로 거절.
- 부분 field 혼합: 검증 경계가 모호하고 상태 조합이 늘어 거절.
- 모든 질문 provider 호출: privacy/policy/grounding gate를 우회하므로 거절.

## 9. 보안·개인정보·접근성·성능 영향

- Privacy: masked free input 전송의 잔여 위험을 local/private에만 승인하고 public/remote는 금지했다.
- Security: client override 금지, ACTIVE/OFFICIAL-only, server-issued fact ID, no-content logging을
  설계했다. key/DSN/secret을 읽거나 출력하지 않았다.
- Accessibility: 생성 방식을 색상만이 아닌 텍스트 배지로 표시하고 loading/fallback의 focus와
  `aria-live` 검증을 요구했다.
- Performance/cost: 최대 8초, concurrency 1, process 30 attempt를 고정했다. actual 비용은 아직 0이다.

## 11. 인간이 반드시 알아야 하거나 승인할 내용

- 현재 승인은 대화에서 합의한 설계이며 제품은 아직 provider-disabled template 상태다.
- 이 서면 명세를 검토·승인한 뒤 후속 실행계획을 별도로 승인해야 구현을 시작한다.
- local/private여도 마스킹 질문은 외부 공급자로 전달되며 국외 처리·계정별 logging 잔여 위험이 있다.
- public/remote/실제 기관 운영, 개인정보 고지, 비용/쿼터 확대는 승인되지 않았다.
- `answer_mode`는 후속 구현에서 API/contract/Web 동시 변경이 필요한 사용자 가시 동작이다.

## 12. AI 내부 구현 세부 — 필요할 때만 보면 되는 내용

- typed provider protocol, fact ID issuer/validator, transport/controller 파일 분리는 후속 계획에서
  현재 코드 의존성을 대조해 정한다.
- existing `httpx`를 재사용하고 새 SDK/production dependency를 넣지 않는다.
- exact settings 변수명은 구현계획에서 현재 loader와 충돌 검토 뒤 고정한다.
