## 5. 설계 결정과 대안

### 선택

아직 구현 결정을 확정하지 않았다. 권고 설계는 generic “증명서/증명서 발급”을
`CERTIFICATE_ISSUANCE + FOLLOWUP`으로 표현하고, 해당 intent 전용 확인 문구와 ACTIVE KB에
대응하는 선택지만 반환하는 category-aware FOLLOWUP이다.

### 이유

OpenAPI의 `FollowupResponse.intent`는 이미 supported intent를 허용하고
`followup_options`도 1개 이상 문자열을 허용한다. 따라서 공개 응답 shape을 깨지 않고
의미만 정확하게 만들 수 있다. 선택지를 ACTIVE KB 범위로 제한하면 가족관계증명서 등 현재
지원하지 않는 대상을 지원한다고 오해시키지 않는다.

### 고려했지만 선택하지 않은 대안

- minimal exact-string special case: 빠르지만 표현 변형마다 누락되고 UNKNOWN 의미를
  계속 오용하므로 비추천이다.
- generic query를 검색해 최상위 KB로 즉시 SUCCESS: 사용자가 원하는 증명서를 추측하게
  되어 “모르면 지어내지 않는다” 원칙에 어긋나므로 제외한다.
- 자유 입력만 요구: 계약 변경은 적지만 시민이 어떤 범위를 지원하는지 알기 어려워
  선택형 접근성·완주율이 낮다.

### 데이터 흐름/상태 변화

Web generic 문구`다. 권고 흐름은 승인 후 `generic certificate cue →
CERTIFICATE_ISSUANCE/FOLLOWUP → certificate 전용 options → 선택 label 재질의 → ACTIVE 검색`
으로 바뀐다.

SUCCESS로 보내지 않고, 선택 이후에도 ACTIVE 검색·grounding gate를 그대로 통과시켜야 한다.
