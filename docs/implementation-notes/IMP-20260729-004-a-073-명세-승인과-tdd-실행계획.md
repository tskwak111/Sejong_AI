## 5. 설계 결정과 대안

### 선택

- one shared typed decision builder가 route→intent→pending slot→identifier→existing
  `ClassifierDecision` route shape→catalog의 fixed first-failure 순서를 소유한다.
- prompt는 exact matrix와 deterministic examples를 사용하고 provider-only catalog를 intent별
  compact row로 만든다.
- production-wire oracle과 exactly-once observer를 controlled-double tests로 먼저 검증한다.
- Tasks 1~5만 offline으로 실행하며 actual은 별도 Task 6 gate로 분리한다.

### 이유

- public parser generic error와 existing `ClassifierDecision` invariant를 유지하면서 internal
  진단만 세분화할 수 있다.
- catalog 사실·ID·coverage·approved example을 보존하면서 actual-eligible prompt bound를
  맞출 수 있다.
- provider body, 잘못된 값, 질문, fixture별 stage를 보관하지 않고도 다음 실패 계층을 안다.

### 고려했지만 선택하지 않은 대안

- provider JSON Schema enum/pattern/conditional: exact Upstage subset이 확인되지 않았고
  cross-field/current catalog 권위를 완전히 대체하지 못해 보류.
- `choice_id` single wire: 승인된 five-key contract를 교체하는 큰 변경이라 기각.
- 질문/catalog 절단·sampling: 공식 선택 가능성을 바꾸므로 기각.
- 명세 승인과 actual 승인 결합: 호출·비용·evidence 불변성을 깨므로 금지.
