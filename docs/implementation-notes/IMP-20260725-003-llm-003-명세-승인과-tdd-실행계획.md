## 5. 설계 결정과 대안

### 선택

- 8개 task:
  1. additive `answer_mode` 계약과 TEMPLATE baseline
  2. pure fact-ID 발급·검증·materialization
  3. synthetic/chat exact settings 분리
  4. source-free one-attempt HTTPX adapter
  5. post-grounding ChatService/idempotency 통합
  6. optional local runtime/lifecycle/runbook
  7. Web label/source/accessibility
  8. security/full regression/versions/optional actual/Draft PR
- 모델은 최대 500자 summary와 request-local ID만 제안한다.
- server가 공식 fact/source/office/policy를 결합하고 오류 하나면 전체 TEMPLATE로 닫는다.
- current `httpx`, `AttemptBudget`, durable idempotency, generated contract toolchain을 재사용한다.

### 이유

이 순서는 계약을 먼저 동결하고 pure validation을 transport보다 앞세워 provider 출력이 도메인
권위를 직접 건드리지 못하게 한다. ChatService는 grounding 뒤에만 protocol을 보고, local
factory만 concrete Upstage runtime을 조립하므로 기본 app과 public 경계가 닫힌다.

### 고려했지만 선택하지 않은 대안

- 기존 synthetic `GeneratedAnswer` 재사용: free fact text 계약이 시민 fact-ID 계약과 달라 거절.
- model output 일부만 template와 혼합: provenance가 불명확하고 상태가 폭증해 거절.
- 새 Upstage SDK: existing HTTPX로 충분하고 새 production dependency 승인이 없어 거절.
- generated summary 완전 미보관: same-key durable replay와 충돌해 provider 중복 방지 품질을
  낮추므로, 기존 safe-response TTL에만 제한적으로 허용.
- 새 DB migration으로 provider-attempt 상태 추가: LLM-003 승인 범위에 없고 현재 claim으로
  동시·완료 replay를 막을 수 있어 거절.
