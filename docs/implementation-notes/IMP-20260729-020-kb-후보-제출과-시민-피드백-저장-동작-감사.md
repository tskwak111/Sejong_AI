## 1. 사용자 요청과 인수 기준

요청은 관리자 `후보 저장 후 승인 요청`이 실패하는 것처럼 보이는 문제를 고치고, 시민
만족/불만족을 실제 반영하며, 불만족에 `기타` 분야·사유와 직접 입력을 제공하는 것이었다.

완료 기준은 다음과 같다.

- 후보 create와 submit 실패를 분리하고, 저장된 `DRAFTED` 후보를 재제출할 수 있다.
- 만족/불만족이 공개 API와 local DB에 저장되고 관리자 화면에 집계된다.
- 기타 상세는 최대 300자, 서버 마스킹 후 정확히 30일만 저장된다.
- raw 상세·질문·답변·provider body·secret·DSN은 저장하거나 출력하지 않는다.
- forward/rollback, pgTAP, API/Web 테스트와 문서·버전을 동기화한다.

전화번호는 `[전화번호]`로 치환하고 일반 설명은 유지한다. 이름·상세주소·고위험 숫자·비정상
유니코드 음성 테스트는 모두 no-write를 확인한다.

## 10. 인간이 반드시 알아야 하는 내용

- 만족/불만족은 이제 actual 모드에서 DB와 관리자 집계에 실제 반영된다.
- 기타 상세는 개인정보를 가린 뒤 30일만 보관한다. 실제 기관 운영 전 법무·기록물 기준으로
  보관정책을 다시 승인해야 한다.
- 후보가 저장됐지만 승인 요청이 실패하면 데이터가 사라진 것이 아니다. 실패 질문 화면의
  `승인 요청 다시 시도`로 `DRAFTED → PENDING_APPROVAL`을 복구한다.
- public/remote 배포, 실제 시민 운영, 새 production dependency, LLM/provider 변경은 수행하지 않았다.

## 11. AI 내부 구현 세부 — 인간이 굳이 이해하지 않아도 되는 내용

- Pydantic discriminated shape와 dataclass invariant가 만족/불만족 필드 조합을 이중 검증한다.
- repository row parser는 category/reason count를 tuple로 제한해 admin contract로 변환한다.
- feedback UI transport 오류는 response body를 읽어 사용자·로그에 노출하지 않는다.
- generated OpenAPI TypeScript가 Web request/response 타입의 단일 출처다.

## 12. 재현·인수인계

1. 저장소 정식 local DB runner로 DB를 시작·검증한다.
2. API `/ready=200` 확인 후 Web actual 모드로 `/chat`을 연다.
3. 답변에서 만족을 누르고 관리자 `/admin`의 시민 의견 집계를 새로고침한다.
4. 불만족→기타 민원→기타 사유→300자 이하 상세를 제출하고 집계·recent를 확인한다.
5. 근거 부족 실패 질문을 사유 확정하고 후보를 저장한다.
6. submit 장애를 재현하면 `DRAFTED` 행에 `승인 요청 다시 시도`가 표시되는지 확인한다.

## 13. 남은 위험·다음 단계

- actual UI 클릭 리허설은 시민 공식 근거 답변, 만족/불만족 저장, 마스킹, 관리자 집계와
  KB 후보 실제 DB 화면까지 완료했다. 후보 생성·제출·재시도 상태 변경은 자동 테스트로 검증했고,
  이 리허설에서는 공식 KB 상태를 추가로 변경하지 않았다.
- 피드백 상세 30일 파기는 local startup/periodic job에 연결됐지만 production scheduler는
  public 배포 설계 전까지 범위 밖이다.
- 품질 지표 API와 피드백 집계는 별도 지표이며 혼합하지 않는다.
- local DB에는 합성 피드백 2건(만족 1, 불만족 1)이 남아 있으며 평가 KPI로 사용하지 않는다.
- public 운영 전 무작위 request ID 제출 방지, rate limit, 실제 인증/RBAC와 production purge
  scheduler는 별도 인간 결정이 필요하다.
