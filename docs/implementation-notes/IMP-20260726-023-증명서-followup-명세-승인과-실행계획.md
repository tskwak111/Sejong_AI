## 5. 설계 결정과 대안

### 선택

5개 independently reviewable task로 분리하고 각 production edit 앞에 실제 behavior test의
RED를 둔다. contract/schema task는 만들지 않는다.

### 이유

OpenAPI는 supported-intent FOLLOWUP과 string options를 이미 허용하므로 generated type
변경은 불필요하다. classifier→server labels→service→Web 순서가 interface dependency와 같다.

### 고려했지만 선택하지 않은 대안

- API/Web을 한 commit에 결합: RED 원인과 review 경계가 불명확해 제외.
- context token option ID 확장: 현재 service가 claim에 option ID를 넣지 않아 YAGNI로 제외.
- admin/region 동시 구현: 독립 subsystem이므로 별도 spec/plan으로 유지.
