## 5. 설계 결정과 대안

### 선택

직접 UI 수동 확인과 저장소에 이미 존재하는 actual Playwright E2E만 사용한다.

### 이유

새 wrapper나 시험 도구를 추가하지 않아 실행 경로와 평가 증거가 기존 권위 runbook에서
갈라지지 않고, 사용자가 원하는 최소 절차에 집중할 수 있다.

### 고려했지만 선택하지 않은 대안

- 평가 공개 저장소 최종 snapshot과 Draft PR: 사용자가 복잡도를 줄이기 위해 취소했다.
- 새 자동 API 질문 runner: 대표 질문은 이번에는 수동 UI로 확인한다.

### 미실행 검증과 이유

Docker/API/Web와 state-changing actual E2E는 사용자가 직접 실행하는 후속 단계다. 조사 시점에
Docker engine이 꺼져 있어 제품 runtime 검증은 수행하지 않았다.
## 9. 보안·개인정보·접근성·성능 영향

- Privacy: 질문 원문·PII·provider body·비밀값을 새 파일이나 로그에 기록하지 않았다. 수동
  시험에는 실제 개인정보 대신 `합성` 표기 데이터를 사용한다.
- Security: env는 key 이름과 SET/MISSING 상태만 검사했고 값을 읽어 출력하지 않았다.
- Accessibility: 사용자가 Web UI에서 키보드 포커스, 모바일 폭, 오류 문구를 직접 확인할
  대표 항목을 안내한다.
- Performance/cost: 새 provider 호출 0, 새 dependency 0. 사용자의 수동 질문은 local profile의
  provider 설정에 따라 제한된 DeepSeek classifier 호출이 발생할 수 있다.
