## 5. 설계 결정과 대안

### 선택

- runtime catalog는 현재 ACTIVE/OFFICIAL projection과 versioned descriptor의 교집합, 최대 20개다.
- descriptor는 topic ID, intent, service name, coverage ID/label, 승인 예시 최대 2개만 가진다.
- provider는 닫힌 route/intent/topic/coverage/pending-slot만 제안하며 답변·출처를 생성하지 않는다.
- server는 topic membership, intent, coverage, current ACTIVE/OFFICIAL을 다시 검증한다.
- exact approved, unique strong lexical, validated semantic topic+coverage,
  validated context facet 중 하나가 있어야 grounding한다.
- 최초 구현은 top-1 KB만 사용하고 여러 KB의 사실을 합성하지 않는다.
- 모호하면 FOLLOWUP, 지원 분야에 대응 topic이 없으면 INSUFFICIENT_GROUNDING으로 닫는다.

### 이유

semantic selection을 모델에 맡기되 행정 사실과 출처 권한을 주지 않으면 자연어 recall과
공식 근거 원칙을 동시에 유지할 수 있다.

### 고려했지만 선택하지 않은 대안

- lexical top-1 강제: 현재 실측 오답·반복 답변을 재현한다.
- provider 답변/출처 허용: 승인 KB 밖 사실과 출처 hallucination 위험이 있다.
- 다중 KB 초기 합성: 상충 절차와 source attribution 복잡도가 커진다.
- semantic selection 결과를 server 검증 없이 신뢰: inactive/draft topic 경계를 깨뜨린다.

## 9. 보안·개인정보·접근성·성능 영향

- Privacy: provider에는 마스킹 질문과 최소 catalog만 전송한다.

- Accessibility: 제품 UI 영향 없음.
- Performance/cost: catalog 최대 20, 요청당 classifier 최대 1이라는 설계 경계 유지.
